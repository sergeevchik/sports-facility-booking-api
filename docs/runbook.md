# Эксплуатация и демонстрация

## Обычная работа

1. Проверить `docker version`, `docker compose version` и наличие свободного места.
2. Один раз выполнить `python3 scripts/bootstrap.py`; существующий .env сохраняется.
3. Запустить `docker compose up -d --build --wait`.
4. Выполнить `docker compose exec -T api python -m app.seed`.
5. Проверить `/health`, Swagger, dashboard и `python scripts/smoke.py`.

`docker compose ps` показывает готовность. `docker compose logs --tail=100 api migrate db`
помогает диагностировать старт. Не прикладывайте полный `docker compose config` или
`docker inspect` к публичному отчёту: они могут раскрыть подставленные env-секреты.

## Порты и прокси

По умолчанию 8000/9090/3000 только на loopback. Для конфликта портов задайте
API_PORT/PROMETHEUS_PORT/GRAFANA_PORT в .env. Проверочные скрипты рассчитаны на стандартные
порты, smoke поддерживает `--base-url`. Основная БД не публикует host-порт.
Тестовый PostgreSQL — отдельный проект и порт 55432.

Если localhost случайно проходит через системный proxy, используйте `curl --noproxy '*'`.
Python smoke/monitoring и Locust используют прямое подключение к локальному стенду.

## Ошибки и действия

| Симптом | Проверка / действие |
|---|---|
| 401 | Проверить локальный API_KEY, заголовок X-API-Key, перезапуск после изменения .env |
| 409 booking_conflict | Выбрать другое время; проверить список, а не повторять POST вслепую |
| 409 facility_has_bookings | Сначала отменить будущие брони; начатые дождаться завершения |
| 422 | UTC-смещение, будущая дата, сетка 30 минут, рабочие часы и вместимость |
| API не стартует | Проверить логи migrate; исправить миграцию/доступность БД |
| /health 503 | Проверить контейнер db и его логи, затем восстановить соединение |
| Grafana без данных | Проверить Prometheus Targets, app_ready и диапазон времени панели |
| Новая .env не подходит старому тому | Пароль PostgreSQL задаётся при первом создании БД; изменение env не меняет пароль внутри существующей БД |
| Нет доступа к GHCR | Проверить видимость пакета и точный тег; частный пакет требует docker login |

Изменение секрета требует согласованной ротации в БД/окружении. Генератор не заменяет
пароли в существующей базе и намеренно не перезаписывает .env.

## Проверка инцидента

`python scripts/check_recovery.py` проверяет сохранность после restart API, затем
временно останавливает db этого проекта и ожидает 503 от readiness и бизнес-API,
200 от /metrics с app_ready=0. finally запускает БД обратно, после чего проверяются
readiness и сохранность брони. Использовать отдельно от нормального нагрузочного замера.
Результат: artifacts/recovery.json. Проверка не удаляет существующие данные.

## Обновление и откат

Перед обновлением запишите текущий APP_IMAGE/digest и версию схемы:
`docker compose exec -T api alembic current`.
Сделайте логическую резервную копию, если данные представляют ценность.

Для обновления: pull выбранного SHA/digest → APP_IMAGE=<image> docker compose up -d --no-build --wait
→ smoke → health → dashboard. Миграции выполняются до API.

Откат **приложения**: выбрать предыдущий проверенный digest и повторить Compose up.
Это безопасно только при совместимой схеме. Автоматический downgrade рабочей БД
не выполняется: миграция 0001 downgrade удаляет таблицы. Для несовместимой миграции
нужен отдельный план восстановления из backup или исправляющая миграция.
Текущая версия содержит одну начальную миграцию; round-trip проверяется только на booking_test.

## Git и релизы

Рабочие ветки → PR → успешные quality/Compose checks → merge в main.
Коммит содержит одно логически связанное изменение. Индивидуальная работа не требует
самоодобрения PR. История сохраняется; force push в main не используется.
Защита основной ветки и результат её настройки фиксируются в отчёте.

GitHub Actions публикует `sha-<полный SHA>` и main; тег v1.0.0 создаёт релизный образ.
При ошибке quality/Compose публикация не выполняется. Для fork PR нет write-публикации.
Негативный CI-сценарий демонстрируется на отдельной ветке, не слиянием дефекта в main.

## Сценарий защиты

1. Показать REPORT.md и модель/транзакционный инвариант.
2. Запустить стенд по README и показать health.
3. Продемонстрировать бронь, конфликт 409, отмену и освобождение времени.
4. Показать конкурентный тест и прямую проверку ограничения PostgreSQL.
5. Показать PR с намеренной ошибкой и неуспешный CI, затем исправление и зелёный CI.
6. Показать SHA, image tag/digest, pull и запуск опубликованного образа.
7. Выполнить запросы, открыть живой Grafana и результаты нагрузки.
8. Объяснить поведение при отказе БД и сохранность данных.

## Известные границы

Один комплекс и один процесс API. Общий операторский ключ не является пользовательской
авторизацией с разграничением доступа. Миграции исполняет владелец БД в учебном локальном
стенде; отдельные production-роли migration/runtime в эту версию не включены.
Переход на несколько workers требует multiprocess-инструментализации метрик.
Процент покрытия — измерение проекта, не подтверждённый преподавателем порог.
