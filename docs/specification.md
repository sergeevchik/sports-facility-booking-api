# Спецификация 1.0

Один спортивный комплекс, разовые бронирования целой площадки оператором.
Реализация собственной предметной логики; пример гостиничного бронирования из курса
использован только как общий ориентир предметной области.

## Данные

Facility: UUID, уникальное непустое имя до 120 символов, sport из tennis/football/
basketball/badminton, capacity 1–100, is_active, created_at.
Тип спорта и вместимость после создания в версии 1 не редактируются.

Booking: UUID, facility_id, customer_ref до 64 символов (буквы/цифры/подчёркивание/
точка/дефис), participants 1–100, starts_at, ends_at, status confirmed/cancelled,
created_at, cancelled_at. customer_ref — идентификатор интеграции, не ФИО/телефон.
В API даты с UTC-смещением, в ответах UTC. Идентификаторы генерирует сервер.

## Инварианты

1. Начало строго в будущем; длительность 30–180 минут включительно.
2. Начало/конец кратны 30 минутам, секунды и микросекунды равны нулю.
3. Весь интервал внутри одного местного дня, 08:00–22:00 Europe/Moscow.
4. participants не превышает capacity; площадка активна.
5. Подтверждённые бронирования одной площадки не пересекаются; границы `[start,end)`.
6. Создание сразу подтверждает бронь. Временного удержания/ожидания оплаты нет.
7. Подтверждённую бронь отменяют до начала. Отмена идемпотентна, включая повторы
   после первоначального времени начала. cancelled_at при повторе не меняется.
8. Нельзя отключить площадку, если у неё есть confirmed с ends_at > now.
9. Записи не удаляются. Прошедшее confirmed не требует фонового изменения статуса.
10. Поиск — снимок доступности, не гарантия последующего создания.

Ограничения времени — настройки комплекса, их значения фиксируются на время работы
стенда. Изменение политики не переписывает существующие бронирования.
Каждый запрос оценивает время по серверным часам; тесты подменяют часы явно.

## HTTP

Все `/api/v1/*` требуют X-API-Key; `/health`, `/metrics`, `/docs`, `/openapi.json`
предназначены для локальных операционных проверок.

| Метод | Путь | Вход / поведение |
|---|---|---|
| POST | /api/v1/facilities | name, sport, capacity; 201 |
| GET | /api/v1/facilities | sport?, is_active?, limit=20, offset=0 |
| GET | /api/v1/facilities/{id} | 200/404 |
| PATCH | /api/v1/facilities/{id}/status | is_active; 200/409 |
| GET | /api/v1/availability | starts_at, ends_at, participants; sport?, limit, offset |
| POST | /api/v1/bookings | facility_id, customer_ref, participants, starts_at, ends_at; 201 |
| GET | /api/v1/bookings/{id} | 200/404 |
| GET | /api/v1/bookings | facility_id?, status?, customer_ref?, starts_at?, ends_at?, limit, offset |
| POST | /api/v1/bookings/{id}/cancel | без тела; 200/409 |
| GET | /health | 200 только при доступной БД, иначе 503 |
| GET | /metrics | Prometheus text; остаётся доступен при отказе БД |

Списки: items, total, limit, offset; limit 1–100, offset >= 0.
Площадки сортируются по name/id, брони — starts_at/id.
Период списка броней означает пересечение; один незаданный конец означает открытую границу.
Поиск доступности возвращает только активные площадки достаточной вместимости,
свободные на **весь** интервал. При одинаковой доступности — стабильная сортировка.

Ошибки: code, message, request_id; у validation_error дополнительно details с
местоположением и типом ошибки, без отражения исходного тела запроса.
401 — ключ; 404 — объект; 409 — конфликт состояния; 422 — данные; 503 — БД.
В ответах присутствует X-Request-ID. Неизвестные поля входных JSON отклоняются.

POST создания брони не имеет ключа идемпотентности. Повтор после потерянного ответа
может вернуть 409; клиент проверяет список по customer_ref/facility/time перед повтором.
Автоматическое небезопасное повторение POST не реализуется.

## Приёмочные сценарии

Создать площадку → найти свободное время → создать бронь → получить 409 на пересечение
→ отменить → убедиться в освобождении → создать новую бронь.
Проверить границы времени, вместимость, соседние интервалы и разные площадки.
Шесть конкурентных одинаковых запросов должны дать ровно один 201 и пять 409.
Отключение площадки одновременно с бронированием сохраняет инвариант доступности.
Данные переживают перезапуск; отказ БД приводит к управляемому 503 и app_ready=0.

## Границы

Операторская интеграция с одним общим ключом, без индивидуальной авторизации клиентов.
Нет платежей, очереди ожидания, изменения времени готовой брони, обслуживания по
календарю, регулярных событий, внешних календарей, уведомлений и отдельного frontend.
Перенос — отмена и новое создание, без гарантии атомарного обмена интервалов.
